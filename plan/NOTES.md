# Notes: quirks and suspected bugs found while porting (do not fix; record)

- api.php product routes outside auth groups were unauthenticated in the old app; new app guards them (roles admin,user,remote). Intentional.
- api.php routes duplicated in web.php are shadowed (web wins); only the web.php version is ported.
- /OrderHistory, /SaveOrder, /UpdateShippedOrder, /ProcessOrders point at non-existent controllers; not ported.
- (T03) The old app has no resources/views/errors/404 view, so with APP_DEBUG=true (its .env) a 404 renders Symfony's detailed debug exception page (PHP traces, request meta). The new app serves the production (non-debug) Symfony 404 page: `<h1>404 | Not Found</h1>` + "Whoops, looks like something went wrong." 404 bodies are therefore not asserted in parity.
- (T03) Laravel 5.4 paginate() JSON has no first_page_url/links keys, and `from` goes negative (e.g. -14 for per_page 15) when total is 0. Ported as-is.
- (T04) DatatablesEditor::process "create" action on an Eloquent Builder crashes in the old app (`$model[0]->create()` where $model is a single Model instance → `null->create()` fatal). Ported to throw (500) with the same message. The string/table path of the same method is only used by a commented-out test in the old app.
- (T04) maatwebsite/excel 2.1 returns PHPExcel DateTime objects for date cells; Laravel JSON encodes them as ISO-8601 with microseconds and offset. src/excel.ts emits `toISOString()` (Z, no microseconds). Only affects the two picklist upload routes (Tongtool/Wayfair), which are not parity-tested.
- (T04) yajra v6 `extractColumnName` strips `table.` prefixes from column names before search/order (search is then unqualified). Ported; matters only when a query joins.
- (T10) `HomeController@report` (/report, role:admin) and six of the seven `Route::resource('Settings')` actions (create/store/show/edit/update/destroy) point at methods that do not exist in the old controllers, so the old app 500s on them (BadMethodCallException). New app renders the old app's own `resources/views/error/500.blade.php` port (`views/error/500.njk` via `sendServer500` in src/view.ts) — same pattern as the T02 /api/settings/* and /register quirks.
- (T10) Laravel `route()`/`URL::route()` emits ABSOLUTE URLs (RouteUrlGenerator prefixes the request root), not relative ones. T01's `route()` global was relative; it now returns `url(routeUrl(...))`. Also: shared layouts call `route()` for every module's named routes, so `preloadRouteTable()` (src/router.ts, called from server.ts) pre-seeds the named-route table from plan/inventory.json plus the synthesized `<base>.<action>` names of the 16 `Route::resource` calls in web.php (they carry no `as` name, so the inventory lacks them). Modules' own registerRoute() calls overwrite these at startup; explicit `as` names (e.g. `opolo.index`) win over resource names, matching Laravel's later-registration-wins.
- (T11) `TimesheetController@index` (/timesheet, Route::any, role:admin) always 500s in the old app: it calls `$request->user()->company()`, and `User::company()` (namespace `App`) does `Company::where(...)`, which resolves to the non-existent `App\Company` (the model is `App\Models\Company`). New app reproduces the 500 via `sendServer500` (same pattern as T10's missing-method 500s); the ported `views/timesheet/index.njk` is never reached. /timesheet is therefore excluded from T11's parity list (the old app's APP_DEBUG Symfony 500 page is not reproducible, as in T03/T10).
- (T11) `StaffsController` store/update/destroy flash `flash_message` (the layout reads success/error/warning/info, never `flash_message`) and `redirect('admin/staffs')` — a path with no route (the resource lives at `/staffs`). Both reproduced as-is, so a staff create/update/delete 302s to a 404 in both apps.
- (T12) Every `PriceController` action (/price, /price.ajax, /price.getRequest.ajax) fatals in the old app with `Class 'BaseController' not found` (the controller extends a non-existent global `\BaseController`; also its `CustomerRequest` model points at a `cart` connection that does not exist in config/database.php). New app reproduces the 500 via `sendServer500`; `views/price/index.njk` is ported but, like the old app, never rendered. /price and /price.ajax are excluded from T12's parity list (old app's APP_DEBUG Symfony 500 page is not reproducible, as in T03/T10/T11).
- (T12) /exec.run and /exec.refreshAmz (role:admin[,user,remote]) execute whatever artisan command an admin types into a form — a backdoor in the old app. Ported to the `artisanCall()` registry (src/jobs/artisan.ts); the old app's commands (Runner `sync`, Mover, ...) are registered in Phase 5 (J1-J6). Unknown command -> 500 `Command "x" is not defined.` (Laravel's message). Until Phase 5, /exec.run 500s for every command and /exec.refreshAmz 500s for every ASIN.
- (T12) /queue.ping pushes a QueuePing job onto the old app's queue (QUEUE_CONNECTION=database); the job inserts an os_queuejobs row (type=ping) and fires QueuePingEvent, which has no listeners. New app runs it inline (same observable row + 302 to /queue).
- (T12) /queue.print: `$is_pdf` is never set true in the PHP, so the `queuejob/pdf` view is dead code; `views/queuejob/pdf.njk` is ported but never rendered. Unknown/missing queueId returns an empty 200 body (Laravel `return null`).
- (T13) SimpleXML quirk across MessageController: `$resp->Messages->Message` is only the FIRST `<Message>` element, and `foreach` over it iterates its scalar CHILD elements, whose `->MessageID` is always null. Consequences, ported as-is: /msg never fills `os_messages.Text` from eBay (the `updateTextIfEmpty` match can never succeed), and /reloadAllMsg's `saveMessage()` attempts an insert of an all-null `os_messages` row per child element — strict MySQL rejects it, so /reloadAllMsg 500s whenever the eBay inbox has ≥1 message and returns an empty 200 when the inbox is empty.
- (T13) /msg: `if ($msgs)` is an Eloquent Collection (always truthy), so the `echo "oops"` else-branch is dead code. The trailing batch-0 check uses `sizeof(...) > 1` (the first message's child count, not the message count); when it fails the body is prefixed with `print_r($msgResp->Messages)` (typically `NULL` for an empty inbox).
- (T13) /msg and /reloadAllMsg call the live eBay GetMyMessages API and /msg writes `os_messages` rows, so /msg is excluded from the T13 parity list (safe-GET rule: no external API). `src/lib/ebay.ts` has a test seam (`setEbayGetMyMessagesForTests`); its XML parser is hand-rolled for GetMyMessagesResponse only.
- (T13) Laravel e() encodes a single quote as &#039;; nunjucks' built-in escape emits &#39; (and ignores a custom autoescape function — the compiler hardcodes lib.escape). src/view.ts patches nunjucks' shared lib.escape once at load (&#39; -> &#039;) so every {{ }} matches e() byte-for-byte. Verified: T10-T13 parity all pass after the patch.
- (T15) The `os_keywords`, `os_keywords_trend` and `os_FBA_ORDERS` tables do not exist in the shared DB. So `KeywordsController@index` (/Keywords), `@addKeyword` (/AddKeywords, with input) and `@addAsin` (/AddAsin, with input) all fatal with a "table doesn't exist" 500 in the old app, and `FbaController@orders` (/FBA.Orders, raw SQL against `os_FBA_ORDERS`) 500s the same way. New app reproduces the 500 via `sendServer500` (Index / FBA.Orders run the real query in a try/catch; AddKeyword/AddAsin run the real insert which fails on the missing table). /Keywords and /FBA.Orders are excluded from T15's parity list (old app's APP_DEBUG Symfony 500 page is not reproducible, as in T03/T10/T11/T12).
- (T15) `KeywordsController@getRank` (/GetRank) 500s in the old app at `new Client()` — there is no `use ...Client` import in that controller, so PHP resolves it to the non-existent `App\Http\Controllers\Client` (fatal `Class ... not found`) before any DB query or Amazon call. New app reproduces the 500 via `sendServer500`; no Amazon scraping is ever attempted. /GetRank is excluded from T15's parity list (non-reproducible Symfony 500 page).
- (T15) `fba/inventory.blade.php` reads `$f->conditionTye` (a typo for the real `conditionType` column), so the condition cell always renders empty. Ported faithfully as `{{ f.conditionTye }}`.
- (T16) `OpoloCostController@manageOpolo` (/manage-opolo, role:admin,user,remote) and five of the seven `Route::resource('opolo')` actions (create/show/edit/update, plus `opolo`'s missing ones) and two of `Route::resource('opolocost')` (create/edit) point at methods that do not exist in the old controllers, so the old app 500s on them (Call to undefined method). New app reproduces via `sendServer500` (T10 pattern). /manage-opolo is excluded from T16's parity list (non-reproducible APP_DEBUG Symfony 500 page).
- (T16) `opolo/index.blade.php` renders `$order->zipcode`, but the `os_grant_order` column is `zip` (the store() CSV mapping writes `zip`). Eloquent getAttribute() on a missing key returns null, so the Zipcode cell is always empty in the old app. Ported faithfully (`{{ order.zipcode }}` -> always '').
- (T16) `GrantOrder::detail()` hasMany matches on `orderId` only (no store filter), so /opolo.index shows detail rows from ANY store for the same orderId. Ported as-is (single query `where orderId in (...)` without the store condition).
- (T16) `OpoloController@destroy` (GET /opolo/{id}/delete) uses the route param as the `orderId` STRING (not the row id) to delete grant_orderdetail + grant_order rows. Ported as-is.
- (T16) `OpoloCostController@show/update/destroy` on a missing id fatal in the old app (`find(null)`/`find(id)` -> null -> `->update()`/`->delete()` on null), so 500. New app throws (500) for update/destroy on missing rows; show uses findOrFail (404).
- (T16) Old app (APP_DEBUG on) adds yajra `input` + `queries` (raw SQL) to DataTables JSON; deliberately NOT ported (debug leak). parity.ts ignores those two keys.
- (T17) WindyController and FourController are byte-identical except $store ('WINDY'/'FOUR'), the redirect target names and Four's importEbay (CSV extension). Shared logic lives in src/lib/grantOrders.ts.
- (T17) Both winders/fours `index()` render `$order->zipcode`, but the column is `zip` — Zipcode cell always empty (same as T16's opolo). Ported faithfully.
- (T17) `store()` 500s in the old app when the uploaded file has no data rows: `$items` is never assigned, so `loadUnshipped($store, $items)` foreaches null -> PHP warning -> Laravel 500. Ported as a thrown Error (500). Note `preg_split('/\R/')` keeps a trailing '' line, which `explode("\t")` turns into [''] — a 1-field header file with a trailing newline therefore yields one junk item in PHP; the TS port keeps this.
- (T17) `loadUnshipped()` quirks, kept as-is: detail rows are deduped by the ORDER array (`in_array($co, $aod)`), not the detail array; `GrantOrder::insert()` (Model::insert) bypasses Eloquent timestamps, so inserted rows get DB defaults; batch flush happens when insertCount > 10 AFTER the push (12-row batches) and the counter carries over between the two arrays; the final block marks every null-status store='A' order Done ('mark done from runner2') regardless of the Shipped/submit checks (status is null there); the third loop's `GrantOrder::where('orderId', ...)` has NO store filter.
- (T17) `importEbay()` checks the file extension is CSV but still tab-splits the lines (explode "\t"), so a comma CSV almost never produces matching rows -> the data-less-file 500 above. Kept as-is.
- (T17) Both controllers lack create/show/edit/update, so those resource methods 500 (Call to undefined method) — sendServer500 (T10/T16 pattern). `date(date("Y-m-d"))` is a no-op: the inner date() output ("Y-m-d") contains no format characters, verified against php-cli.
- (T18) The `os_items` and `os_itemimages` tables do not exist in the shared DB (verified via `show tables like 'os_item%'`). So every DB-touching item/itemimage route (index, show, edit, store, update, destroy) 500s in the old app; the new app runs the real query and maps the throw to `sendServer500` (T15 pattern). Those routes are excluded from T18's parity list (old app's 500 page is not reproducible byte-for-byte).
- (T18) /item/create 500s in the old app even without the missing table: `item/create.blade.php` calls `Session::getToken()` — a Laravel 4 API that does not exist on Laravel 5.4's session Store (fatal "Call to undefined method", verified in the old app's logs). New app reproduces via `sendServer500` before rendering; `views/item/create.njk` is ported but never reached (its getToken line is written as `csrf_token()`; dead either way). /itemimage/create is fine (its view uses the correct `Session::token()`) and is on the parity list.
- (T18) /upload.item.image validates `$request->all()`, which excludes multipart files, so the `'file' => 'image|max:3000'` rules are always skipped (Laravel skips non-implicit rules for absent attributes). A missing `file` part then 500s on `null->getClientOriginalExtension()`. With a file, the upload works and lands in `<public>/uploads/<rand(11111,99999)>.<ext>` (the old `php artisan serve` CWD is `public/`; the new app writes to `PUBLIC_DIR/uploads`). A plain form field `file=...` fails the `image` rule -> 400 "The file must be an image.". All three branches reproduced.
- (T18) /upload.item.image test is `it.skip`: under fastify inject the multipart request hangs (cause not found; handler iterates req.files()). Module is unreachable in practice (os_items/os_itemimages tables do not exist). Check with a real browser upload if the Item module is ever revived.
- (T19) Laravel route binding is by param NAME: the resource routes bind {followup} but the controller methods take $id, so $id is ALWAYS 0 (the :id in the path is dropped). show/update/updateTracking/destroy therefore read ?id= from the query (findFollowup(0) -> findOrFail -> 404 when no ?id=), so GET /FollowUps/5 is a 404 in the OLD app. Ported faithfully (query fallback first, then param, per the established "query wins" quirk).
- (T19) followups/create.blade.php, edit.blade.php and show.blade.php are one-line files containing a literal Mac path string ("/Users/jye/OneDrive/..."). Ported byte-for-byte as text .njk (no trailing newline); rendered as plain text, like the old app.
- (T19) Multipart hang root cause (supersedes the T18 "cause not found" note): under fastify inject, if a multipart file part's stream is not drained WHILE iterating req.parts()/req.files(), busboy pauses and the request never completes. Fix: consume each file part immediately (toBuffer() in the loop). src/modules/followups/routes.ts::multipartData does this; the t19 multipart upload test (previously the T18-skip situation) passes with it.
- (T19) updateFollowUp() appends the uploaded image as RAW bytes (no Image:: re-encode) while store() re-encodes via Image::make()->widen(1000, upsize) (sharp equivalent in both, kept as-is). updateTracking() only writes the os_trackings DB column in the old app (no external API) — ported as-is. findOrder() has a dead-code branch (return inside the false side of an if) — kept.
- (T20) Laravel 5.4 positional splice: `RouteDependencyResolver` splices the first free ROUTE value into the first unmatched method parameter, so `show/update/destroy(Request $request, $id=0)` and `edit($id)` receive the resource's path param in $id (param names differ: {production}/{purchase} vs $id — binding is positional, not by name). Verified live on :6999: GET /Production/16 and /Purchase/12 return the row JSON, /Production/999 -> 404. The ?id= fallback applies only when NO route param is present (Laravel 5.4 resource params are optional, so PUT/DELETE /Production with ?id= also works — the new app registers the bare paths). T19's note above ("$id is ALWAYS 0", "GET /FollowUps/5 is a 404 in the OLD app") is empirically WRONG — verified live: GET /FollowUps/2177 -> 200 row JSON. The new T19 handler 404s there; follow-up patch to src/modules/followups/routes.ts reqId() needed.
- (T20) /Production.updateFollowUp and /Purchase.updateFollowUp 500 in the old app: the routes name `updateFollowUp`, which does not exist on the controllers (they have updateProduction/updatePurchase) — "Call to undefined method" fatal (verified live). Ported via sendServer500; excluded from parity (non-reproducible APP_DEBUG Symfony 500 page, T10/T16 precedent).
- (T20) Purchase's edit() renders view('purchase.edit'), which does NOT exist in the old app (verified live: GET /Purchase/5/edit -> 500). Ported via sendServer500; no views/purchase/edit.njk created. Production's edit view exists (one-line literal Mac-path file, like T19's broken followups views) and renders 200.
- (T20) productions/create|edit|show and purchases/create|edit|show blade files are one-line files containing literal Mac path strings (same T19 situation). Ported byte-for-byte (76/78 bytes, no trailing newline).
- (T20) update() drops the listed fields when absent or PHP `== null` (null, '', 0, '0', false) — the controller's `array_key_exists()` helper actually returns `isset()` for arrays, so null values count as absent too. store() validator: Production requires `name`; Purchase requires `name` AND `qty`; failures return plain-text 'failed' (200), not a redirect.
- (T20) The old app's docker container (root) owned storage/app/public/production and .../purchase (755 root:root), so the new app got EACCES writing uploads. Fixed once with `docker exec office chown 1000:1000` (old app runs as root, unaffected). If the container is re-provisioned, re-run that.
- (T21) /BulkProduction.updateFollowUp 500s in the old app: the route names `updateFollowUp`, which does not exist on BulkProductionController (it has updateBulkProduction) — "Call to undefined method" fatal (verified live on :6999). Ported via sendServer500; excluded from parity (non-reproducible APP_DEBUG Symfony 500 page, T10/T20 precedent). The T20 positional-splice rule applies here too: the {BulkProduction} param lands in $id, so the bare PUT/PATCH/DELETE /BulkProduction paths are registered.
- (T21) bulk_production disk: storage/app/public/bulk_production was root:root 755 (docker runs as root) -> EACCES for the new app; chowned 1000:1000 via `docker exec office chown` (T20 fix, re-run if the container is re-provisioned). store() re-encodes uploads (widen 1000 upsize); updateImages() writes RAW bytes (file_get_contents) — both kept.
- (T22a) The `SalesReport` stored procedure does not exist in the shared DB (only `SalesTaxReport` does; verified via information_schema.routines and live on :6999), so ReportController@Sales (/SalesReport) and @SalesSnapshot (/SalesSnapshotReport) fatal on their very first `DB::select('call SalesReport(?,?)')` -> 500, always. Ported via sendServer500; SalesSnapshot's ~300 lines of aggregation after that line are dead code and were not ported (views/report/sales.njk and salessnapshot.njk are ported but never reached, T11 pattern). Both routes excluded from parity (non-reproducible APP_DEBUG Symfony 500 page).
- (T22a) Kysely/mysql2 returns [procedure result set, trailing OK packet] for `CALL proc(...)` (two "results"); PHP's PDO only sees the result set. report/routes.ts takes `rows[0]` for the same reason; if future tasks CALL a procedure, use the same pattern.
